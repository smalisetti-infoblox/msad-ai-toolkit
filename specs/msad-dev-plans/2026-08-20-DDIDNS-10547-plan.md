# DDIDNS-10547 Plan — Backend: allow changing replication scope on Microsoft DNS zone update

## Summary

DDIDNS-10547 implements the DDIDNS-9464-approved exception to DDIDNS-7732's write-once replication-scope rule, **scoped to Forward zones only** for this pass (Auth/Primary zones remain blocked — see `HANDOFF.md` for why: Q1/Q3 design questions about in-place update vs. AD migration and rollback only apply to Auth/Primary, and Forward zones already have a complete, working, rollback-safe agent-side implementation).

**This is not greenfield** — an existing draft PR (#511) already implements most of this, but it has one real bug (confirmed by both an automated Copilot review comment and independent verification against the diff): it **also unintentionally relaxes Auth zone updates**, directly contradicting its own PR description's stated scope ("Auth Zone Updates: Intentionally unchanged"). This plan's primary work is fixing that regression, not writing new logic.

## Context

- **Jira:** DDIDNS-10547 (Task, To Do, unassigned) → parent Story DDIDNS-10566 → parent epic DDIDNS-7732
- **Repos involved:** `ddi.cloud.proxy.middleware` only. `ddi.msad.agent` needs **no changes** for this task (see Assumptions).
- **Legacy-scope decision (resolved 2026-08-20, see HANDOFF.md):** the Update-path allow-list for a scope-*change* target must exclude `legacy`, exactly like the Create-path. `legacy` may only ever be set via the separate MSAD→DDI sync path (`cq-source-msad`/`cloud.discovery`), never via a user-initiated Create or Update.

**Blocking finding — confirmed by reading the actual diff (`gh pr diff 511`), not just the PR description:**

`AuthZoneUpdateHandler.Handle` (pkg/interceptor_handlers.go, ~line 1258-1266) was modified in the exact same way as `ForwardZoneUpdateHandler.Handle` — the original write-once block:
```go
if existingZoneEPMD.MSADConfig.ReplicationScope != zoneEPMD.MSADConfig.ReplicationScope {
    return nil, ddiErrors.Wrap(errCannotUpdateReplicationScope)
}
```
was replaced with the same allow-list-validate-and-permit logic used for Forward zones. This directly contradicts the PR's own description: *"Auth Zone Updates: Intentionally unchanged—remain write-once (agent-side dependency not yet ready)."* Copilot's automated review on the PR independently flagged this: *"Also unintentionally enables Auth Zone scope changes."*

**This must be reverted.** Auth zone updates must continue to hard-block any scope change, exactly as before PR #511. Auth/Primary zone support is future work gated on the still-open Q1 (in-place update vs. AD migration) and Q3 (rollback) — see `HANDOFF.md`.

**Note on how this happened (not a copy-paste accident):** the PR branch has two separate commits — `bc5e80a` "allow replication scope change on Forward Zone update" and a second, distinctly-titled `f5814c5` "add replication scope change support for Auth zones." This was deliberate work by the PR author, later contradicted by their own final PR description ("Auth Zone Updates: Intentionally unchanged") — a scope disagreement between what was built and what was described, not an accidental side effect of shared code. The PR body's "Test Results" section independently repeats the same false claim ("Auth Zone remain write-once (existing tests unchanged)") even though the diff renames the Auth-zone test case and rewrites its fixture data. **Whoever executes this plan should communicate the revert as resolving a scope disagreement in the commit/PR message, not silently correct a typo** — the original author may have intended the Auth-zone work and just failed to update the description; worth a heads-up rather than an unexplained revert.

**Sequencing note (not a bug, just an ordering dependency):** PR #511 currently calls `isValidMSADReplicationScopeForStubZone`, which is the function's name on current `master`. PR #507 (DDIDNS-10519, already bounded-reviewed and ready for merge — see `specs/msad-dev-plans/2026-08-20-DDIDNS-10562-plan.md`) renames this function to `isValidMSADReplicationScopeForZoneCreate` when it merges. **Recommend merging PR #507 before completing PR #511**, so PR #511 can be rebased onto the renamed function directly rather than needing a second follow-up rename commit.

### ddi.msad.agent: No Changes Needed

`DnsConditionalForwarderZoneController` already has a complete, working, rollback-safe implementation of scope changes via `Set-DnsServerConditionalForwarderZone -ReplicationScope` (verified in HANDOFF.md). The middleware is the sole authoritative validation gate for the Update path — unlike Create, which validates independently at both middleware and agent layers (DDIDNS-10519/10521), Update's scope-change decision (is this actually a change? is the new value valid?) is made entirely in middleware using both old and new zone state, which the agent's Update RPC handler doesn't have visibility into on its own. No agent-side code change is required for this task.

**Assumption (stated, not silently made):** if this assumption is wrong — e.g., if the agent's `IsValidUpdateDnsZoneRequest` should independently re-validate a changed target scope as defense-in-depth, matching the Create path's pattern — that would be a separate follow-up task, not blocking this one, since middleware already fully gates invalid/legacy values before any request reaches the agent.
