# DDIDNS-10547 Plan (v2 — scope expanded) — Backend: allow changing replication scope on Microsoft DNS zone update

## Summary

**This plan supersedes the earlier same-day version**, which scoped this task to Forward zones only. Per explicit user decision (2026-08-20, see `HANDOFF.md`), scope is now **all zone types** (Auth/Primary and Forward). This also corrects a factual error in the original Jira task description and this toolkit's own earlier documentation: Forward zone's agent-side implementation was claimed to be "already complete with rollback" — it is not. Both zone controllers have the scope-change PowerShell call commented out as dead code, and Forward zone's dead rollback code additionally references the wrong cmdlet.

## Context

- **Jira:** DDIDNS-10547 (Task, To Do, unassigned) → parent Story DDIDNS-10566 → parent epic DDIDNS-7732. Task description needs a Jira update to reflect the expanded scope (tracked as a follow-up in this plan's execution).
- **Repos involved:** `ddi.cloud.proxy.middleware` (validation, mostly already done via existing PR) and `ddi.msad.agent` (new work, no existing PR).
- **Resolved decisions (see `HANDOFF.md` for full rationale):**
  1. Scope covers all zone types now, not Forward-only.
  2. `legacy` may never be a target scope on Update (only creatable via sync, never via Create or Update) — reuse the Create-path allow-list, don't duplicate it.
  3. No zone-type-specific transition restrictions — `local`↔`domain`/`forest` is allowed uniformly for both Auth/Primary and Forward zones (explicitly overriding a stricter guard a previous engineer had written into Primary zone's dead code — recorded as a known, accepted risk, not silently dropped).

**Changes (by type):**

**Modifications — `MSADAgent/Agent/Core/DnsInfoControllers/DnsInfoZoneControllers/DnsPrimaryZoneController.cs`:**
- Uncomment and enable `Set-DnsServerPrimaryZone -ComputerName '{serverIp}' -Name '{zoneName}' -ReplicationScope '{replicationScope}'` in the `Update()` method's `case "Primary":` branch, only when `replicationScope` actually differs from the freshly-fetched `currentReplicationScope` (avoid a no-op PowerShell call when the scope isn't changing).
- **Do NOT restore** the commented-out local-exclusion guard (`if (currentReplicationScope.ToLower() == "local" || replicationScope.ToLower() == "local") throw ...`) — per Decision 3, this is deliberately dropped, not overlooked. Leave a comment explaining why it's absent (reference this plan / DDIDNS-10547) so a future reader doesn't think it was missed.
- Add validation: if the new `replicationScope` (case-insensitive) is `"legacy"` and it differs from `currentReplicationScope`, throw a clear, distinguishable exception before calling `Set-DnsServerPrimaryZone` (mirrors `IsValidReplicationScopeValue()`'s Create-path exclusion from DDIDNS-10521 — reuse that method if accessible from this class, or add an equivalent check here if not, but do not invent a third independent allow-list).
- Add rollback: track whether the scope-set call actually ran (i.e., scope was changing). If any exception occurs later in the same `Update()` call (e.g., during zone-transfer-settings configuration), and the scope was already changed, attempt a best-effort revert to `currentReplicationScope` via a second `Set-DnsServerPrimaryZone` call in the `catch` block — log success/failure of the revert but never let a revert failure mask the original exception (mirror the try/catch-around-revert pattern from Package 2's Forward-zone fix below).

**Modifications — `MSADAgent/Agent/Core/DnsInfoControllers/DnsInfoZoneControllers/DnsConditionalForwarderZoneController.cs`:**
- Uncomment and enable `Set-DnsServerConditionalForwarderZone -ComputerName '{serverName}' -Name '{zoneName}' -ReplicationScope '{replicationScope}'` in `Update()`, only when scope is actually changing (compare against the already-fetched `originalReplicationScope`).
- Add the same legacy-target rejection as Primary zone.
- **Fix the rollback cmdlet bug** in the commented-out `catch` block: it currently uses `Set-DnsServerForwarder -ReplicationScope` (wrong cmdlet — that's for the conditional-forwarder server list, not zone scope). Change to `Set-DnsServerConditionalForwarderZone -ComputerName '{serverName}' -Name '{zoneName}' -ReplicationScope '{originalReplicationScope}'`, matching the actual set-command's cmdlet. Uncomment and enable this corrected version.

## Cross-Repo Constraints

- **Validator reuse, not duplication:** the legacy-target rejection in both agent controllers should reuse or exactly mirror `IsValidReplicationScopeValue()` (from `DnsZoneRequestHandler.cs`, DDIDNS-10521/PR #617) rather than introducing new, separately-maintained checks.
- **Middleware and agent are independently deployable for this task** — no merge-order dependency, but both are needed for the feature to work end-to-end in production. Note this in both PR descriptions.

## Assumptions

- PR #511's existing Auth+Forward validation logic in middleware is correct as-is and needs no code changes — only its description needs correcting.
- The exact names of the Agent.Tests files for `DnsPrimaryZoneController` and `DnsConditionalForwarderZoneController` will be discovered by the implementing agent (following this repo's established per-controller test file naming pattern) rather than guessed here.
- No middleware-side rollback is needed — rollback is entirely an agent-side (PowerShell/AD) concern, matching how the existing (buggy) dead code was structured.

## Risks

- **Local-exclusion removal (Decision 3) is an accepted, explicit risk** — if real AD environments reject or mishandle `local`-involving Update transitions for Primary zones specifically, this will surface as a production failure, not a test failure (our tests only validate against mocked `IPowerShellManager`, not real AD). Mitigation: the fix is a single shared validation point if this needs to be reintroduced later — not scattered.
- **Windows CI is the only real verification** for the agent changes — local Mac testing can only validate the C# logic against mocked PowerShell execution, not real cmdlet behavior.
- **Rollback correctness is itself unverified against real AD** — the mocked-`IPowerShellManager` tests confirm the *code path* calls the right revert command with the right arguments, but not that Windows Server DNS actually accepts a rapid-fire set-then-revert sequence cleanly. This is the same class of residual risk as Decision 1's "treat the cmdlet as supported" call.
