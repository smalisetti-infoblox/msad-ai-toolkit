# DDIDNS-10562 Plan — Backend: Domain/Forest replication scope on Microsoft DNS zone creation

## Summary

Story DDIDNS-10562 requires `ddi.cloud.proxy.middleware` and `ddi.msad.agent` to accept and validate Domain and Forest replication scope during Auth, Reverse Auth, and Forward zone creation, per epic DDIDNS-7732. **This work is not greenfield** — both linked tasks already have substantial, tested, CI-green draft/open PRs. This plan documents current state, surfaces one real cross-repo validator-drift finding for the bounded code-review loop to resolve, and sets up scenario traceability for the two tasks.

**Blocking finding carried into this plan (self-flagged by PR #617's author, confirmed by reading the diff):**
- PR #617's `IsValidReplicationScopeValue()` allow-list includes `legacy` (to mirror the existing `Update` validator), but `dns.config`'s `validateStubZoneReplicationScopeNotLegacy()` and middleware's zone-creation validator (both confirmed in this repo's current code) **reject `legacy` at creation**. This is a live validator-drift risk across the three-repo mirror (dns.config ↔ middleware ↔ agent) for the **Create** path specifically — Update paths are correctly `legacy`-inclusive everywhere.
- **This MUST be resolved in the bounded code-review loop** (`/msad-dev-execution` Step 4): either tighten PR #617's Create allow-list to exclude `legacy` (matching dns.config/middleware), or provide an explicit justification for the asymmetry, logged in the review ledger.

- **Prior work found via `gh pr list`:** no other open/merged PRs found for DDIDNS-10519 or DDIDNS-10521 beyond the two above.
- **Constraints:** `ddi.msad.agent` is Windows-only; local testing on Mac not possible, verification is via Windows CI (`windows_node_ddi_msad_agent_label`) — already passing on PR #617.

## Cross-Repo Constraints

- **Validator sync (Create path):** dns.config's `validateStubZoneReplicationScopeNotLegacy()`, middleware's `isValidMSADReplicationScopeForZoneCreate()`, and agent's `IsValidReplicationScopeValue()` (Create call sites only) must all reject `legacy`. Currently dns.config + middleware do; agent's Create path does not yet (PR #617 as-is). **This is the plan's one required fix.**
- **Update path is intentionally different:** all three layers correctly allow `legacy` on Update (immutability/write-once enforcement is separate from the scope-value allow-list) — do not "fix" this by also rejecting `legacy` on Update.

## Risks

- **Validator drift (the finding above):** if not fixed, a `legacy`-scope zone could be created via the agent's Primary/Forward path while being rejected at the dns.config/middleware layer for the same operation — inconsistent behavior across the stack. Mitigation: fix in code-review loop, add the missing test case.
- **Windows CI dependency:** PR #617's fix (removing `legacy` from Create allow-list) requires a Windows CI re-run to confirm; local Mac verification is not possible for this repo.

## Open Questions

None blocking — the one substantive question raised in PR #617 (should `legacy` be in the Create allow-list) is resolved by this plan: **no**, exclude it, to match the cross-repo contract.

**Clarified during review (user, 2026-08-20):** `legacy` replication scope must still be *discoverable* — existing AD zones with `legacy` scope are synced into DDI via `cq-source-msad` + `cloud.discovery` (a separate MSAD→DDI read path, not touched by this plan). Confirmed via code inspection: `cq-source-msad/resources/services/dns/zones.go` reports whatever `replication_scope` the live AD zone has (no allow-list), and `cloud.discovery/pkg/adapters/overlay/msad/cq_fetchers.go` passes it through to DDI's `b1ddi` overlay unchanged. This is architecturally independent of `ddi.msad.agent`'s Create/Update validators (DDI→MSAD write path) — **confirms, does not change, this plan's fix**: users still can never *create* a `legacy`-scope zone through DDI; they can only ever see one that was synced in from an existing AD environment. Per this clarification, changing an already-`legacy` zone's scope further is explicitly deferred to later work (tracked under DDIDNS-10566's broader scope-change story). Toolkit's `references/repo-topology.md` updated to document `cq-source-msad` and `cloud.discovery` as part of the MSAD topology (new "Sync / Discovery Repos" section).
