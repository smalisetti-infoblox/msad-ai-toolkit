# DDIDNS-10543 Plan — ddi.msad.collector: map ZONE-00x agent error codes to gRPC status on Update/Delete

## Summary

`ZonesServer.Create` already classifies the agent's `ZONE-00x` error codes into distinguishable gRPC status codes via `util.GetErrorCode`/`util.ErrorCodeToStatus`. `Update` and `Delete` don't — they wrap the raw agent error text in a plain `errors.New(...)`, which isn't a gRPC status at all, so it surfaces to `ddi.cloud.proxy.middleware` as opaque `codes.Unknown`, losing all `ZONE-00x` semantics. This is a pre-existing, standalone gap — not required by or blocking any other in-flight epic work — filed as its own task.

**This is not greenfield** — an existing draft PR (#241) already implements this correctly and completely, with TDD-verified tests (confirmed red before green) and full CI green (Jenkins, lint, nilaway). This plan's job is to verify it and fix one small, already-identified nit, not write new logic.

**Verified independently (not just trusting the PR description):**
- `util.ErrorCodeToStatus()`'s `default` case returns `nil` for both an empty `errCode` (regex found nothing) and a non-empty-but-unmapped `errCode` — confirming the Copilot comment is accurate: the current log message can't distinguish these two cases.
- The diff applies the identical `GetErrorCode`/`ErrorCodeToStatus` pattern already used by `Create` to both `Update` and `Delete`, and adds the previously entirely-unmapped `ZONE-005` (invalid zone name) → `codes.InvalidArgument` case, which applies uniformly to all three RPCs (not just Update/Delete).
