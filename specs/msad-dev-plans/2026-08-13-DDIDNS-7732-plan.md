### PR 508: DDIDNS-10542 — Middleware: Idempotency (Duplicate Prevention + Rollback)

**Repo:** `Infoblox-CTO/ddi.cloud.proxy.middleware`  
**Status:** DRAFT (2026-08-12 15:22 UTC)  
**Author:** Seshachalam Malisetti (+ Claude Sonnet 5)

**What it does:**
- **Pre-flight duplicate check:** `AuthZoneCreateHandler` and `ForwardZoneCreateHandler` now check if zone already exists in DDI Postgres BEFORE calling MSAD `Create` RPC
  - Query: `SELECT id FROM zones WHERE account_id=? AND view_name=? AND fqdn=?`
  - Returns `codes.AlreadyExists` if found (prevents MSAD zone creation)
- **Rollback on failure:** If MSAD zone is successfully created but subsequent DDI write fails, automatically rollback the MSAD zone via `Delete` RPC
  - Uses best-effort pattern (logs failures but doesn't mask original error)
  - Mirrors existing Stub zone rollback implementation

**Test coverage:**
- Duplicate-zone fixture: verifies MSAD `Create` is never called when zone exists in DB (`gomock .Times(0)`)
- Rollback tests: MSAD Create succeeds, downstream handler fails, `Delete` called with correct zone ID
- All tests green

**DDIDNS-7732 Phase 1 AC addressed:**
- ✅ AC (implicit): "Idempotency — duplicate creation attempts prevented"

**Dependencies:**
- None on PR 507 (independent middleware changes, can merge in any order)
- Complements PR 507 (both address middleware gaps for Auth/Forward zones)

**Known gaps (intentional, out of scope):**
- A handful of non-MSAD-specific error paths (VPC proxy validation, read-only-provider check) between MSAD Create and DDI write are NOT rolled back. Would require broader refactoring of shared logic with non-MSAD providers. Flagged as possible follow-up.

**Review checklist:**
- [ ] Pre-flight duplicate check uses correct query shape
- [ ] `codes.AlreadyExists` returned when zone exists
- [ ] Rollback invoked at correct points (tag validation failure, DDI write failure)
- [ ] Rollback does not mask original error
- [ ] Gomock assertions verify calls
- [ ] Test coverage ≥80% for new code
- [ ] `go test ./...` passes
- [ ] `gofmt -l` clean

**Action:** Review and merge

### PR 241: DDIDNS-10543 — Collector: Error-Code Mapping for Update/Delete

**Repo:** `Infoblox-CTO/ddi.msad.collector`  
**Status:** DRAFT (2026-08-12 15:15 UTC)  
**Author:** Seshachalam Malisetti

**What it does:**
- `ZonesServer.Create` already maps agent `ZONE-00x` error codes → gRPC status codes via `GetErrorCode` + `ErrorCodeToStatus`
- `Update` and `Delete` did NOT — they wrapped raw error text in `errors.New()`, surfacing as opaque `codes.Unknown` with no semantics
- Applied the same mapping to `Update` and `Delete` that `Create` already uses
- Added `ZONE-005` case to `ErrorCodeToStatus` → `codes.InvalidArgument` (invalid zone name)

**Changes:**
- `pkg/svc/zones/zones.go`: Applied `GetErrorCode` + `ErrorCodeToStatus` to Update/Delete paths
- `pkg/util/util.go`: Added `ZONE-005` → `codes.InvalidArgument` mapping
- `pkg/util/util_test.go`: Added test case for `ZONE-005`
- `pkg/svc/zones/zones_test.go`: Added table-driven test cases for Update/Delete (zone-already-exists, access-denied, zone-not-found, invalid-zone-name, unknown code)

**Test coverage:**
- New `ZONE-005` case in `TestErrorCodeToStatus`
- Update/Delete test cases mirror Create behavior (table-driven)
- All tests green

**Note:** This is a **pre-existing gap**, discovered during DDIDNS-7732 investigation. Create already had this behavior; Update/Delete now match. Not strictly required for Phase 1, but improves error consistency.

**DDIDNS-7732 Phase 1 AC addressed:**
